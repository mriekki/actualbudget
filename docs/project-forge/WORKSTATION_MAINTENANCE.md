# Workstation maintenance via /setup

The existing `/setup` command installs missing declared prerequisites; `/setup repair` repairs broken prerequisites; `/setup status` inspects workstation tools read-only; and `/setup update` is the explicit, reviewed ongoing upgrade path.

## Exact source and preview

Use `python tools/project-forge-setup/maintenance.py status` to inspect installed versions and eligibility, or `status --record-check` during normal non-read-only `/setup` to retain only a local check timestamp in ignored `.project-forge/`. At a normal `/setup` call, suggest a check approximately every 30 days if there is no newer recorded check. This is not a scheduled/background service.

Use `python tools/project-forge-setup/maintenance.py update [--tool rtk ...]` for the default non-mutating preview of selected safe candidates. The exact tool IDs, manager commands, installed versions, pins and SHA-256 in this output define the approval scope. Only after the Builder explicitly accepts the reviewed action, run the same selection with `--apply --plan-sha256 <approved-value>`. Changed data invalidates approval.

The helper reads `DEV_ENVIRONMENT.json` and the selected `tools/dev-environment/catalog/*.json` copies generated by Bootstrap. It never guesses package IDs or uses `upgrade --all`. The states `MANAGER_CHECK` and `PINNED_RELEASE_UPGRADE` indicate upgrade eligibility, not a claim that a newer registry version exists. Preview the underlying manager's available version when feasible and expose it to the Builder. Homebrew/winget apply commands are intentionally package-specific; those managers may resolve a newer release at execution time.

## Boundaries

- The currently reviewed generic package-manager allowlist is RTK, GitHub CLI, Git and fnm only. All other catalog entries require separate specialized upgrade policy; Docker Desktop, VS Code and Python are explicitly excluded from this generic updater.
- Never automatically update project-pinned toolchain versions, application dependencies/lockfiles, generated package provenance, Project Forge-managed assets, Docker Desktop, SSH trust, or deployment targets.
- Package-managed Project Forge updates remain owned by `/project-forge-update`. Modern Web Guidance remains on its approved exact version and independent from normal workstation tool updates.
- Missing selected catalog entries, unsupported managers or unknown pinned-release integrity are manual-review gaps. An adopted repository without Bootstrap's selected tool catalog must use its existing, human-approved setup/update mechanisms instead of an invented Project Forge catalog.
- A platform package-manager update may affect other programs and is not transactionally reversible. Report failures honestly and verify installed versions, doctor and relevant runtime checks afterward. Never deploy or restart production as a consequence.
- Version checks and update previews never install packages or mutate repository state. Only explicit apply can update tools, and the existing setup approval and Project conventions remain authoritative.
